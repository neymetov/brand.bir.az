## Медиа-конвейер, 2026-08-05

20. **Бакет публичный или приватный — не подтверждено.** Модель данных
    сделана так, чтобы работать в обоих случаях: блок хранит и `id` файла
    Strapi, и `url`. Для публичного бакета достаточно `url`; для приватного
    `url` — снимок presigned-ссылки, которая протухнет, и настоящим
    источником становится `id` (`lib/strapi/media.ts` → `resolveImageUrl`).
    Что осталось сделать после ответа: при приватном бакете — резолвить
    ссылку на рендере (или поднять image-proxy, §1 ТЗ), при публичном —
    можно ничего не менять.
21. **CSP допускает `'unsafe-inline'` для скриптов и стилей.** Для стилей это
    требование самого Next.js (инлайнит критический CSS). Для скриптов —
    временно: строгий вариант требует nonce-пайплайна, а он завязан на
    подключение GTM (§1 ТЗ: GTM через `next/script`, теги не грузятся до
    consent). Пересмотреть, когда будет подключаться аналитика.
22. **`next/image` пока не используется** — блок рендерит `<img>`.
    `images.remotePatterns` уже собирается из env и заработает сразу, но
    переход на `next/image` отдельная задача: у приватного бакета
    оптимизатор Next.js не сможет ходить за файлом без прокси (см. №20).

## Палитра цветов, 2026-08-05 (ColorPalette, Figma node 254:2484)

23. **Печатных значений (PMS/CMYK) нет в токенах.** `birds-tokens` хранит
    только экранные цвета; PMS/CMYK в макете — плейсхолдеры (у всех образцов
    одинаковые `244 C` и `00/41/01/00`). В демо-данные дашборда подставлены
    те же плейсхолдеры. Настоящие значения должна дать бренд-команда —
    сейчас их взять неоткуда.
24. **Цвет подписей на карточке считается по контрасту, а не берётся из
    макета.** В Figma текст на всех образцах белый, но в палитре есть
    «Birbank White» — на нём белым по белому не прочитать ничего. Поэтому
    тон подписи выбирается по яркости заливки (WCAG-формула,
    `readableTextColor`). Если дизайн предполагал другое поведение для
    светлых образцов (например, тёмную рамку или серую плашку) — сказать.
25. **Заливка образца — произвольная строка, а не токен ДС.** Админ вводит
    любое CSS-значение цвета. Это осознанно: палитра документирует в том
    числе цвета, которых нет в `--bb-*` (печатные, партнёрские, исторические).
    Но значит, stylelint такие значения не проверяет — контроль только на
    стороне редактора.

## Кнопки действия, 2026-08-05 (ActionButtons, Figma node 257:3008)

26. **Вариации кнопки не перечислены типом — это осознанно.** В макете их 10
    (Download, Go to, Copy JSON/SVG, Download PDF/PNG/AI/PPTX, Check Figma/
    Drive) и пользователь предупредил, что список вырастет. Любая вариация
    складывается из трёх независимых полей: поведение (`download`/`link`/
    `copy`) × иконка × её позиция. Новая вариация = новая комбинация в
    редакторе, код менять не нужно. Добавление именно новой ИКОНКИ требует
    положить SVG в `public/icons/dashboard` и дописать имя в
    `DashboardIconName` + `actionIcons`.
27. **`download` для кросс-доменных ссылок не работает** — браузер
    игнорирует атрибут и просто открывает файл. Это ограничение самого
    браузера, не кода. Пока медиа лежит на своём домене (или проксируется),
    вопрос не встаёт; если файлы будут отдаваться прямо с чужого CDN,
    скачивание придётся проводить через свой роут.
28. **Скачивание файла из медиатеки задаётся ссылкой, а не выбором файла.**
    В отличие от MediaBlock, у кнопки нет пикера медиатеки — адрес вводится
    строкой. Когда Strapi подключат, стоит переиспользовать тот же пикер,
    иначе у приватного бакета ссылка протухнет (см. №20).

## Витрина шрифта, 2026-08-06 (FontfaceViewer, Figma node 259:3101)

29. **Файлы шрифтов нужно залить в медиатеку Strapi.** Блок выбирает шрифт
    из CMS (`/api/media?kind=font`), но самих файлов пока нет — как и
    Strapi. До этого образец рендерится системным шрифтом: параметры и
    копирование работают, а начертание показывается не то. HAL Matex и
    Inter, на которые ссылаются токены, тоже нигде в проекте не лежат.
30. **Лицензии на шрифты не проверены.** Выкладывание файла в медиатеку
    делает его доступным для скачивания всем, у кого есть доступ к сайту.
    Для HAL Matex (коммерческий) это может нарушать лицензию — уточнить у
    юристов/бренд-команды, прежде чем заливать оригиналы. Возможный
    компромисс — подмножество глифов только для показа.
31. **Трекинг задаётся в процентах и переводится в `em`.** В макете
    «-3%», в CSS применяется `-0.03em` (при 96px это -2.88px — совпадает с
    Figma). Если дизайн подразумевал абсолютные пиксели, значения разойдутся
    на других кеглях.
32. **Начертание описывается двумя полями: `weight` и подписью
    `styleName`.** Подпись — свободный текст («Bold»), она не влияет на
    отрисовку; за неё отвечает `weight` + сам файл. Рассинхрон возможен:
    админ может написать «Bold», а вес указать 400. Проверок нет —
    осознанно, потому что имена начертаний у шрифтов не стандартизованы.

## Форматированный текст, 2026-08-06 (TextBlock + lib/richText)

39. **Редактор построен на `document.execCommand`.** Метод помечен
    устаревшим, но поддерживается всеми браузерами и остаётся единственным
    способом форматировать выделение без собственной модели документа.
    Альтернатива — Tiptap/Slate/Lexical: сотни килобайт и своя модель ради
    семи кнопок. Если появится потребность в таблицах, изображениях внутри
    текста или совместном редактировании — переезд на полноценный редактор
    станет оправдан.
40. **Набор форматирования намеренно узкий**: жирный, курсив,
    подчёркивание, зачёркивание, ссылка, список, ПРОПИСНЫЕ, сброс. Заголовки
    внутри текста не даются — за них отвечают `title`/`description` блока и
    отдельные секции; иначе структура страницы уехала бы в контент.
41. **Капс меняет сами символы, а не стиль.** `text-transform: uppercase`
    не переживает копирование текста со страницы, а в документации капс
    обычно нужен именно в содержимом. Обратно к строчным одной кнопкой не
    вернуть — это осознанный размен.
42. **Вставка из буфера обеззараживается до простого текста.** Иначе из
    Word/Google Docs приезжают чужие стили и разметка. Форматирование
    накладывается кнопками уже после вставки.

116. **Каждая сессия начинается со ввода пароля** (требование пользователя,
     2026-08-10). Требование состояло из двух частей, и выполнимы они
     по-разному.

     **Часть 1 — «пароль нельзя сохранять в браузере». Сайт этого не
     гарантирует, и обещать обратное было бы неправдой.** Браузеры намеренно
     игнорируют `autocomplete="off"` у полей пароля: Chrome, Firefox и Safari
     перестали его слушаться как раз потому, что сайты им злоупотребляли, а
     менеджеры паролей — тем более. Сделано всё, что реально действует:
     у поля было `autocomplete="current-password"` (прямое приглашение
     подставить сохранённый пароль) — заменено на `new-password`, при котором
     Chrome и Safari сохранённое не подставляют; добавлены `autocomplete="off"`
     на форму и атрибуты-подсказки 1Password, LastPass, Bitwarden и Dashlane.
     Пользователь, который всё же захочет сохранить пароль, сохранит его.
     Единственная настоящая управа здесь организационная — не раздавать один
     пароль на всех (см. №114).

     **Часть 2 — «каждая сессия со ввода пароля». Вот это выполнено.**
     У cookie и раньше не было `maxAge`: она сессионная и умирает с
     браузером. Но одного этого мало — Chrome и Firefox с настройкой
     «продолжить с того же места» ВОССТАНАВЛИВАЮТ сессионные cookie после
     перезапуска, то есть «закрыл браузер = вышел» браузером не
     гарантируется. Поэтому введены два срока:
     — **простой 1 час**: нет запросов дольше часа — вход заново. Считается от
       последней активности, а не от входа: значение перевыпускается по ходу
       работы прямо в миддлвари;
     — **общий предел 12 часов** от ввода пароля, никакой активностью не
       сдвигается. Без него вкладка, которая сама себя обновляет, продлевала
       бы сессию вечно и пароль не спрашивался бы никогда.
     Прежний срок в 2 суток (№114) этим заменён.

     Перевыпуск идёт не на каждом запросе, а когда прошла половина окна:
     перепечатывание — это шифрование, а после закрытия иконок гейтом (№113)
     через миддлварь проходит каждый значок на странице. Плата — размытая
     граница: фактический простой лежит между получасом и часом.

     Флаги cookie вынесены в `sessionCookieOptions()` и одни на вход и на
     продление: разойдись они хоть в одном поле — продление тихо сняло бы
     httpOnly посреди работы.

     Проверено на живом стенде: свежая сессия продления не получает (рано);
     выпущенная 40 минут назад — получает, с httpOnly и без Max-Age;
     просроченная по простою (печать со сроком 1 с и ожидание 65 с, чтобы
     пройти запас iron на расхождение часов) → 307 на /login; старше 12 часов
     → 307 на /login.

     **Попутно выяснилось и стоит помнить:** подделать «давно неактивную»
     сессию, передав прошлое время в `createSessionCookieValue`, нельзя —
     срок простоя iron ставит по собственным часам при запечатывании, а
     аргумент влияет только на отметки внутри значения. Первая версия и
     тестов, и живой проверки была из-за этого неверной и показывала успех
     там, где ничего не проверялось.

     **Не сделано, рядом лежит:** после выхода кнопка «назад» может показать
     страницу из кэша браузера — гейт при этом не срабатывает, потому что
     запроса на сервер не будет. Лечится заголовком `Cache-Control: no-store`
     для HTML. Не трогал: это отдельное изменение, влияющее на скорость всех
     страниц.

122. **Переносы строк в TextBlock пропадали** (сообщено пользователем,
     2026-08-10: «как бы в редакторе ни переносил предложения на новую
     строку, в превью остаётся на месте»).
     Воспроизведено в браузере, и оказалось хуже описанного: строки не только
     слипались, но и **перемешивались** — набранные «Первая/Вторая/Третья»
     давали `ретья строкаВторая строкаТПервая строка`.
     Причина одна на оба симптома. По Enter contentEditable в Chrome строит
     `<div>` (замерено: `one<div>two</div><div>three</div>`), а `div` не был
     в белом списке DOMPurify в `RichTextEditor`. DOMPurify выбрасывает
     неразрешённый тег, **сохраняя содержимое**, — разбиение исчезало. Дальше
     срабатывал второй эффект: результат санитизации не совпадал с тем, что в
     редакторе, эффект синхронизации переписывал `innerHTML` прямо во время
     набора, и каретка улетала в начало — отсюда текст задом наперёд.
     Исправлено тремя правками:
     — `div` добавлен в белый список редактора (при рендере он всё равно
       становится `<p>`, см. TAG_ALIASES);
     — `defaultParagraphSeparator` выставлен в `p`, чтобы Enter сразу давал
       абзац, а не div;
     — эффект синхронизации больше не трогает DOM, когда значение вернулось
       эхом собственного `onChange` (сравнение с `lastEmitted`). Это и есть
       починка каретки: она держится при любом расхождении санитайзера с
       разметкой браузера, а не только для div.
     Заодно: одиночный перенос в **обычном** тексте (вставка из письма,
     импорт, контент старого формата) теперь рендерится как `<br>`. Раньше
     абзац давала только пустая строка, а одиночный Enter схлопывался в
     пробел — та же жалоба, только для не-HTML контента.
     Проверено в живом редакторе: панель и холст совпадают символ в символ,
     порядок строк верный, Shift+Enter по-прежнему даёт перенос внутри абзаца.
     **Осталось косметическое:** самая первая строка остаётся голым текстовым
     узлом, а не абзацем (так работает contentEditable), поэтому отступ до
     второй строки меньше, чем между следующими абзацами. Панель показывает
     ровно то же, что превью, так что расхождения между «как набрал» и «как
     вижу» нет. Лечится инициализацией пустого редактора как `<p><br></p>`,
     но тогда в CMS может попасть пустой абзац — не стал делать без спроса.

123. **Фон экрана логина — видео** (файл от пользователя, 2026-08-10).
     `Bir Pay Motion.mp4` переименован в `public/images/login-background.mp4`:
     пробелы в имени пришлось бы экранировать в каждом адресе, и рано или
     поздно кто-нибудь забыл бы.
     Картинка `login-background.jpg` осталась фоном страницы и `poster`
     видео — она видна мгновенно, пока ролик грузится, и остаётся насовсем,
     если он не запустится (экономия трафика в мобильных браузерах, отказ
     автовоспроизведения, ошибка сети). Экран входа не должен зависеть от
     того, доехало ли видео.
     `muted` обязателен: без него браузеры запрещают автовоспроизведение
     (звуковой дорожки в файле и нет). `playsInline` — для iOS, иначе Safari
     разворачивает видео на весь экран поверх формы. `pointer-events: none` —
     чтобы слой не перехватывал клики у формы.
     При системной настройке «меньше движения» видео скрывается и остаётся
     картинка: для части людей движущийся фон — это мигрень, а не украшение.
     **Видео внесено в `loginAssets` миддлвари.** Без этого оно уходило бы в
     редирект на /login и фон молча не появлялся — ровно та ошибка, что была
     с картинкой (№47) и с иконками (№113). Тест на это добавлен.
     Проверено в браузере без сессии: видео играет (readyState 4, время идёт),
     1920×1080, ни одного запроса с ошибкой или редиректом; при
     «меньше движения» — `display: none`.
     **Требует решения: вес.** 21,4 МБ на 11 секунд 1080p — это ~15 Мбит/с,
     впятеро-вдесятеро больше обычного для фонового цикла (1,5–3 Мбит/с, то
     есть 2–4 МБ). Файл грузится ДО входа, то есть у любого, кто открыл
     адрес. На мобильном интернете это примерно 15–20 секунд трафика впустую
     (картинка-подложка при этом покажется сразу, так что экран не пустует).
     Перекодировать нечем: `ffmpeg` в системе нет, ставить его без спроса не
     стал. Команда, когда дойдут руки:
     `ffmpeg -i login-background.mp4 -vf scale=1280:-2 -c:v libx264 -crf 28 -preset slow -an -movflags +faststart out.mp4`
     Отдельно стоит добавить `webm` вторым `<source>` — он обычно ещё на
     треть легче при том же виде.
     Побочное: при «меньше движения» файл всё равно скачивается — его прячет
     CSS, а не отменяет загрузку. Отменять в JS значило бы либо расхождение
     разметки сервера и клиента, либо мигание. При лёгком файле это перестанет
     иметь значение.
