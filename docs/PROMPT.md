# BirDS — brand.bir.az: техническое задание для Claude Code

Этот файл — сводка архитектурных решений по сайту `brand.bir.az` (внутренняя
документация дизайн-системы BirDS), принятых в ходе обсуждения с Elshan
(design system lead, Birbank/Kapital Bank). Используй его как отправную точку
для реализации — не как окончательную спецификацию: там, где решение помечено
"открытый вопрос", уточняй у пользователя перед тем, как продолжать.

---

## 1. Стек проекта (весь BirDS, не только brand.bir.az)

### Frontend
- Next.js + TypeScript (strict mode), App Router
- Node.js 20 LTS для сборок (не последняя версия)
- i18n: next-intl, три локали AZ/EN/RU — все три добавляются одной правкой;
  отсутствующий ключ перевода должен вызывать краш сборки, НЕ fallback
- State/Data: Redux Toolkit + axios; формы — react-hook-form
- Стили: Sass/SCSS + stylelint; никаких произвольных значений вместо токенов
  дизайн-системы (stylelint должен это ловить)
- Дизайн-система: использовать готовые компоненты приватной ДС и общей
  UI-библиотеки; bespoke-компоненты — только если в ДС нет аналога
- Анимация: framer-motion
- Аналитика: GTM через inline `next/script` (`afterInteractive` для GTM,
  `lazyOnload` для прочих тегов); не грузить теги до consent, PII не в URL,
  соблюдать CSP
- SEO: next-sitemap; canonical/OG/hreflang
- Окружения: сборка под dev/qa/preprod/prod через `env-cmd` + переменная
  окружения с именем окружения; env-файлы не смешивать

### Качество кода
- ESLint (airbnb/eslint-config-next) + security-набор (risxss, xss,
  no-unsanitized, jsx-a11y)
- husky + lint-staged
- commitlint (conventional commits, lowercase subject, header ≤ 100)

### Observability / Security
- OpenTelemetry (OTLP gRPC) + prom-client (Prometheus)
- Никакого сырого `dangerouslySetInnerHTML` на rich-text из CMS — парсить
  через `html-react-parser` или санитизировать на входе (DOMPurify)

### CMS
- Strapi v5 на TypeScript, PostgreSQL
- Плагины: users-permissions (public read), i18n (AZ/EN/RU),
  provider-upload-aws-s3, CKEditor, color-picker, publisher
  (плановая публикация/снятие), populate-deep
- Медиа: S3-совместимое хранилище (`forcePathStyle` + явный endpoint,
  кастомный CA — TLS-верификацию НЕ отключать); приватные бакеты →
  presigned URL с конечным сроком → фронту нужен image-proxy; публичный
  `baseUrl` — без прокси; источник медиа всегда в CSP (`img-src`/`media-src`)
- Контент-модель: `collectionType`/`singleType`, `draftAndPublish: true`;
  секции — из переиспользуемых компонентов, сгруппированных по доменам;
  контроллеры/роутеры — чистые `createCore*` фабрики без кастомной логики
- Локализация: компоненты по умолчанию НЕ локализованы (`localized` — на
  атрибуте родителя); видимость по локали, не по глобальному флагу;
  каноничная локаль-источник — AZ (fallback на неё)
- Контракт ответа — стабильный, deep-populatable
- PUT single-type (Strapi v5): вложенные компоненты БЕЗ поля `id` (иначе
  400), медиа — числовыми upload-id, конверт `{"data":{...}}`

### Общее
- Docker (отдельный prod-Dockerfile)
- CI: GitLab CI или Jenkins + SonarQube (должен быть зелёным)
- Секреты только из env/keystore, никогда в коде/конфигах/`.env` в репо

## 2. Контекст BirDS-платформы

BirDS — мульти-брендовая дизайн-система для экосистемы Birbank/Kapital Bank
(Азербайджан). Крылья экосистемы:
- **Fintech:** birbank.az (Retail), private.birbank.az (Private),
  birbank.business (Business), birbankinvest.az (Invest)
- **E-commerce:** birmarket.az
- **Payments:** m10.az, million.az
- **Loyalty:** birbonus.az (сквозной)
- **Ecosystem hub:** bir.az
- **HR Tech:** careers.bir.az — тот же бренд, что bir.az, но с бежевым
  акцентом; ⏸ ПРИОСТАНОВЛЕН на дизайн-стороне с 2026-07-09, не расширять
  токены/схемы дальше существующего черновика без явного подтверждения

Каждый сайт — свой домен, своя Strapi-инстанция. AZ — каноничная локаль.
Брейкпоинты 960/1440/1920px. Финансовые данные (курсы, ставки калькулятора)
НИКОГДА не в CMS — только из выделенных API.

Monorepo: `birds-tokens/` (SCSS), `birds-contract/` (TS-контракты),
`strapi-schemas/`, `@birds/ui` (React-компоненты ДС).

## 3. brand.bir.az — что строим в этой задаче

Отдельный внутренний сайт: документация ДС (гайдлайны + tone of voice),
живая страница компонентов и changelog. **НЕ публичный** — доступ только
по паролю (см. §6).

### 3.1 Информационная архитектура (плоская, 4 верхнеуровневых раздела)

```
/guidelines/[brand]           — per-brand: логотип, цвет, типографика,
                                 иконография, imagery. Готовые бренды:
                                 ecosystem, retail, business, invest, private
                                 (birmarket/m10/million — отложено)
/guidelines/foundations       — общее, не привязанное к конкретному бренду
/tone-of-voice/[brand]        — per-brand (тон СИЛЬНО различается между
                                 брендами — НЕ единый голос с нюансами)
/components                   — каталог + /components/[category]/[component]
/changelog                    — ОБЩИЙ для всех брендов/компонентов, не
                                 разбит по разделам на верхнем уровне
```

### 3.2 Реальные значения бренд-токенов (см. §5 — файлы токенов приложены)

```ts
type FintechBrand = 'ecosystem' | 'retail' | 'business' | 'invest' | 'private';
type PartnerBrand = 'birbonus' | 'birmarket' | 'm10' | 'million';
type BrandKey = FintechBrand | PartnerBrand;
```

- `ecosystem` = bir.az (чёрный акцент), `retail` — дефолтный бренд (задан и
  на `:root`, работает без атрибута `data-brand`)
- Fintech-бренды имеют ПОЛНУЮ тему (`--bb-brand-default/hover/pressed/disabled`
  + вся семантика text/bg/border)
- Партнёрские бренды — ТОЛЬКО плоские `--bb-partner-*` акцентные токены, без
  каскада/состояний. В будущем партнёрские бренды получат СОБСТВЕННЫЕ
  компоненты (не только тему для существующих) — списки поддерживаемых
  брендов должны быть per-component, не единый глобальный список на 5/9

### 3.3 Раздел /components — живой playground

Требования:
- Компоненты рендерятся client-side как настоящие React-компоненты из
  `@birds/ui` — НЕ iframe, НЕ песочница. 100% соответствие продакшн-коду
- Переключение бренда — дропдаун (не таб — список брендов на компонент
  растёт со временем), СКОУПЛЕН ЛОКАЛЬНО на каждый демо-блок компонента,
  НЕ глобально на `html`/`body`. Несколько демо на одной странице могут
  одновременно показывать разные бренды
- `data-brand` ставится на `<div>`-обёртку конкретного демо, каскад CSS уже
  всё разрешает сам (см. §5, слой `--bb-*` уже существует и активен)
- Панель props (react-hook-form) — состояние НЕЗАВИСИМО от состояния бренда
- Под каждым компонентом — блок с исходным кодом, читается на СБОРКЕ из
  реального файла компонента в репозитории ДС (`fs.readFile` + shiki для
  подсветки) — НЕ хранится вручную в Strapi, чтобы не расходиться с кодом
- Кнопка "копировать" — и для блока кода, и для отдельных токенов
  (`navigator.clipboard.writeText`)
- Референсная реализация этой части уже есть — см. приложенные файлы
  `playground-demo/` (types/brand.ts, ComponentPlayground.tsx,
  BrandSwitcher.tsx, CodeBlock.tsx, PropsPanel.tsx, getComponentSource.ts,
  пример страницы Button). **Пути импортов и путь до `packages/ui` в
  `getComponentSource.ts` — placeholder, нужно свериться с реальной
  структурой monorepo.**

### 3.4 Копирование SVG-содержимого

- Для SVG из кода ДС (иконки в `@birds/ui/icons`) — читать на сборке тем же
  паттерном, что код компонентов
- Для SVG, загруженных как медиа в Strapi (иллюстрации/логотипы гайдов) —
  runtime `fetch(presignedUrl)` → `.text()` → clipboard. Presigned URL может
  истечь при долго открытой вкладке — либо кэшировать текст сразу при
  загрузке страницы, либо перезапрашивать свежий URL перед копированием
- Если SVG рендерится инлайново (не просто `<img src>`) — санитизировать
  через DOMPurify перед вставкой в DOM, не доверять файлу вслепую

### 3.5 Визуальный редактор гайдлайнов — craft.js

**Выбран craft.js**, НЕ готовый плагин Strapi Page Builder (последний
зависит от стороннего SaaS `pagebuilder.wc8.io` — неприемлемо для
внутреннего банковского инструмента).

craft.js — только движок (state management, drag-n-drop, сериализация),
БЕЗ готового UI — весь визуальный слой (тулбокс, панель настроек, canvas,
индикаторы выбора) строится с нуля как обычные React-компоненты, стилизуется
токенами `--bb-*` самого сайта brand.bir.az.

**Хранение — Strapi Dynamic Zone, НЕ сырой JSON-blob:**
- Контент гайд-страниц хранится как Dynamic Zone из тех же переиспользуемых
  компонентов, что и остальной контент сайта (существующий паттерн)
- Резолвер craft.js должен ЗЕРКАЛИТЬ схему Dynamic Zone 1-в-1: каждый
  Strapi-компонент (`sections.text-block` и т.п.) имеет соответствующий
  craft-блок с теми же полями
- Craft-блоки — ОБЁРТКИ над настоящими компонентами `@birds/ui`, не
  дублирующая логика: `<TextBlockCraft>` рендерит `<TextBlock>` из ДС,
  добавляя только `craft` static config для редактора
- Рекомендуется отдельный пакет `@birds/craft-blocks`, растущий независимо
  от `@birds/ui` (можно добавлять craft-блоки, не трогая публичный рендер)
- **Синхронизация Strapi ↔ craft.js — не live, а snapshot-on-save:** при
  открытии редактора — `GET` из Strapi → маппинг Dynamic Zone → узлы craft.js
  → `<Frame data={...}>`. Все правки живут в браузере до нажатия "Сохранить"
  → `query.serialize()` → обратный маппинг → `PUT` в Strapi, поле
  перезаписывается целиком. Одновременное редактирование двумя людьми одной
  страницы → последний сохранивший перезаписывает — принят как риск при ≤2
  редакторах
- **Единый реестр блоков** — рекомендуется единый registry.ts/JSON, из
  которого генерируются и `allowedComponents` Dynamic Zone в Strapi, и
  `resolver` craft.js, чтобы оба списка НИКОГДА не расходились вручную
- Dynamic Zone — плоский список компонентов на одном уровне. УТОЧНИТЬ У
  ПОЛЬЗОВАТЕЛЯ: нужна ли вложенность (колонки внутри секции и т.п.) — если
  да, потребуется Component-внутри-Component в Strapi

### 3.6 Changelog — гибридная модель

- Источник версий — semver / conventional commits ИЗ РЕПОЗИТОРИЯ дизайн-
  системы (commitlint conventional commits УЖЕ стандарт проекта)
- Strapi хранит только editorial-обёртку: человеческое summary, категория,
  теги (breaking/new/fix) — привязанные к конкретной версии
- НЕ полностью ручной ввод в Strapi (риск расхождения с реальными релизами)
- Точный механизм передачи версий в Strapi (build-time парсинг CHANGELOG.md
  vs webhook при релизе) — ОТКРЫТЫЙ ВОПРОС, требует решения перед
  реализацией этого раздела

### 3.7 Live-превью документов

- **PDF** — `react-pdf` (обёртка PDF.js), рендер постранично в браузере,
  работает с приватными presigned URL без проблем (клиент сам скачивает и
  рендерит)
- **PPTX** — НЕ использовать Office Online Viewer / Google Docs Viewer
  (требуют публичный URL — несовместимо с login-gated сайтом). Вместо этого:
  серверная конвертация PPTX → PDF через LibreOffice headless в Docker
  (`libreoffice --headless --convert-to pdf`), триггер — Strapi lifecycle
  hook при загрузке `.pptx` в медиатеку, результат кладётся рядом в тот же
  приватный бакет, показывается тем же PDF-компонентом

## 4. Авторизация brand.bir.az

- **Два SHARED-аккаунта** (не персональные логины, не таблица
  пользователей): viewer-пароль для общего доступа к сайту, отдельный БОЛЕЕ
  СТРОГИЙ admin-пароль для `/admin` (там живёт craft.js-редактор)
- `/admin` — это СОБСТВЕННЫЙ роут ВНУТРИ данного Next.js-приложения, НЕ
  Strapi admin panel (тот живёт отдельно, на своём домене/сервисе) — не
  путать эти два "admin" при разработке
- Хранение: bcrypt-хэши обоих паролей в env/keystore
- После успешного логина — signed httpOnly cookie (`iron-session` или JWT) с
  ролью `viewer` | `admin`
- Next.js middleware: `/admin/*` требует роль `admin`, всё остальное —
  минимум `viewer`; `admin` даёт доступ и туда, и туда
- Максимум 2 редактора; ПОЛНОЦЕННЫЙ audit trail НЕ нужен — осознанно принято
  (команда маленькая, редакторов всегда видно вручную)

## 5. Приложенные файлы токенов

В `tokens/` — реальные файлы из пакета `birds-tokens` (обновлённая единая
версия от 2026-07-09, объединяющая все бренды в одном месте):

- `_colors.scss` — семантические `--bb-*` токены на `:root` + миксин
  `-brand()` + 5 активных блоков `[data-brand='ecosystem'|'retail'|
  'business'|'invest'|'private']` + партнёрские `--bb-partner-*` + один
  ⏸-блок `[data-brand='hr-tech']` (НЕ трогать, пауза на дизайне)
- `_primitives.scss` — примитивы (Tailwind-палитра + брендовые палитры +
  альфа + HR Tech draft-примитивы)
- `README.md` — статус по брендам, структура файлов, история решений
- `typography-raw.json` — СЫРОЙ дамп из Figma Variables API (коллекция
  Typography): FontFamily, FontSize, LineHeight для Display/Heading/
  Paragraph/Label/Caption, по 4 режимам (см. ниже)
- `radius-spacing-raw.json` — сырой дамп коллекций Radius (один режим,
  не отзывчивый) и Spacing (4 режима)

**ПОДТВЕРЖДЕНО ПОЛЬЗОВАТЕЛЕМ (2026-08-05): брейкпоинтов не 3 (960/1440/1920,
как было ошибочно записано ранее), а 4 РЕЖИМА** — Mobile / Tablet / Desktop /
Desktop+. Используй именно эту сетку из 4 режимов при генерации адаптивной
типографики/spacing, а не 3-брейкпоинтную модель.

**`typography-raw.json` и `radius-spacing-raw.json` — это СЫРЫЕ данные, НЕ
готовый SCSS.** У нас нет реального `_typography.scss` как образца
синтаксиса/именования функций (в отличие от `_colors.scss`/`_primitives.scss`,
которые являются настоящими файлами репозитория) — переводить JSON в SCSS-
миксины нужно, сверяясь со стилем уже существующих `_colors.scss`/
`_primitives.scss` (те же паттерны: `@use`, функции-примитивы, комментарии
с источником), а не изобретая новую конвенцию.

**ВАЖНО: даже с этими двумя JSON это НЕ полный комплект пакета.** Модуль
`_misc.scss`/`_index.scss` (если в них есть что-то помимо ре-экспортов) в
этой выгрузке ОТСУТСТВУЕТ. Возьми недостающее из реального репозитория
`birds-tokens/`, не додумывай.

## 7. Открытые вопросы, требующие уточнения у пользователя перед реализацией

1. Нужна ли вложенность секций в гайд-страницах (колонки внутри секции) —
   влияет на структуру Dynamic Zone и craft.js resolver (§3.5)
2. Источник данных changelog: build-time парсинг CHANGELOG.md репозитория
   ДС vs webhook при релизе (§3.6)
3. Полный набор `birds-tokens` (§5) — недостающие модули нужно взять из
   реального репозитория, не восстанавливать по памяти
4. `Spacing/margin` в `radius-spacing-raw.json` резко скачет между режимами
   (16 → 189 → 341) — не похоже на обычный spacing-шаг, вероятно боковой
   отступ страницы. Подтвердить смысл токена у дизайнеров перед
   использованием в общей spacing-шкале
5. Label/L1-L4 и Caption/C1-C2 не масштабируются между режимами (одинаковые
   значения на всех 4) — уточнить, это осознанное решение (мелкий текст не
   адаптируется) или недосмотр в Figma
